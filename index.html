Claude Code : pourquoi c'est différent

Un agent dans le terminal

  • Utilise toutes les CLIs : GitHub CLI, npm, rg, kubectl ...
  • Édition automatique des fichiers
  • CLAUDE.md : contexte partagé avec les règles
  • Commands : répéter les prompts facilement
  • Hooks(juin) : déterministe
"J'ai commencé à pousser toutes les mécaniques : le CLAUDE.md pour le contexte partagé, les commands pour répéter les prompts facilement." "Avant, il fallait écrire un petit moment. Maintenant, une commande pouvait écrire beaucoup de code." Mode YOLO (skip permissions) car tâche de fond sur environnement de dev, pas de risque. "Je lançais toujours en mode skip permissions pour éviter d'être prompté."

Le hic

Plus on donne de contexte, meilleur est le résultat

Mais chaque action = beaucoup de tokens

Fenêtre de contexte : 200K tokens

/compact = session morte

Sonnet 3.7 (fév 2025) : 200K tokens. Ça part très vite : system prompt, CLAUDE.md, outils, chaque fichier lu/édité consomme du contexte. Au début, pas du tout optimisé, ni côté cache ni côté utilisation. Il y a eu des réductions de plus de 30% sur la conso de tokens lors de certaines grosses mises à jour de modèle. Quand on atteint la limite, /compact compresse tout et on perd le fil — session morte. Depuis Opus 4.6 (fév 2026) on est à 1M par défaut.

La parade

  • 1. Découper le travail en sessions courtes
  • 2. Produire un artefact à chaque étape
  • 3. Nouvelle session = contexte propre + artefacts précédents
Les fichiers générés (plans, résumés, specs) vivent sur le disque. Ils permettent de repartir avec un contexte neuf sans perdre l'historique. Le prompt varie peu, le contexte stable profite du cache KV (~4-5x moins cher). Les hooks Claude Code automatisent la sauvegarde. On découpe le plus petit possible : plus c'est petit, plus c'est facile à développer, tester, déployer. Et ces fichiers structurés... c'est exactement ce que le SDD formalise.

C'est le Spec-Driven Development

Spec
→
Plan
→
Tasks
→
Implement

Chaque étape = un artefact qui sert de point de départ pour la suivante

Chaque étape dans une session séparée (contexte propre)

C'est le workflow de base du SDD, tel que proposé par SpecKit. "Surtout, ne faites pas l'erreur de lancer à la chaîne dans le même prompt. Ça ne sert à rien. Lancez dans une nouvelle session. Ça repart avec un contexte clair." "Le plan : c'est lui qui doit vraiment avoir toute l'intelligence parce que c'est lui qui analyse le code et qui dit 'Ok, là, tu dois avoir cette construction. Tu dois changer ce fichier.' Si vous avez des limitations de coût, c'est ici que vous devez mettre votre modèle le plus performant." Mon workflow perso ajoute des étapes (simplify, review, doc) — on verra ça en démo devant l'app.

1

Spec-First

Spec puis jetée

Spec-Anchored

Spec-as-Source

Le code est généré

Pas encore d'outil en prod

"Le SDD ne vient pas du tout du monde de l'IA. Mais là, ça va nous intéresser dans le contexte de l'IA." SpecKit, Kiro (cf. présentation de Mehdi pour ceux qui ont vu, c'est totalement ça). Le niveau 2 (Spec-Anchored) : "C'est le niveau qui m'intéresse, que j'ai essayé de mettre en place." Le niveau 3 (Spec-as-Source) : "Vous modifiez la doc, ça modifie le code. Vous n'écrivez jamais le code." Den Delimarsky, créateur de SpecKit (ex-GitHub), embauché par Anthropic. A travaillé sur la planification et les tâches de Claude Code, maintenant sur MCP. Ref: Birgitta Bockeler (Thoughtworks) — martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html

Est-ce que le SDD est indispensable ?

Non.

Tout le monde fait un peu du SDD dès qu'il planifie avant d'implémenter.

La différence : enregistrer les specs comme artefacts persistants.

"Aujourd'hui, Claude Code vous propose automatiquement : il vous fait la planification, il vous dit 'ok, clear le contexte', et on repart du plan. C'est la bonne pratique." "Quand vous utilisez d'autres outils qui ne sont pas aussi développés, une fois que vous faites votre planification, demandez à générer un artefact dans votre commande plan." Quand c'est utile : projet structuré (type entreprise), modèle moins performant (Mistral → "clairement c'est une catastrophe sur la gestion du code"), besoin de traçabilité, agent factory. "Depuis un mois, vous avez 1M de tokens de contexte au même prix que 200K. Ça change beaucoup."

Où se placer dans la boucle ?

Outside
Vibe coding
L'humain décrit, l'agent fait tout. Mais la qualité interne compte toujours.
In the loop
Revue ligne par ligne
L'humain inspecte tout. Mais il devient le goulot d'étranglement.
On the loop
Harness Engineering
Améliorer le harnais (rules, specs, workflow), pas l'artefact.

C'est exactement ce que j'ai fait sur ai-board. Voyons les résultats.

Ref: Kief Morris (Thoughtworks) — "Humans and Agents in Software Engineering Loops" (martinfowler.com) C'est exactement ce qu'on fait : améliorer le CLAUDE.md, la constitution, le workflow. Pas corriger le code individuellement, mais corriger le processus qui produit le code. Quand un résultat ne va pas : on ne corrige pas l'artefact, on modifie le harnais. "Maintenant, voyons ce que ça donne concrètement sur ai-board."

Recommandations

  • Adaptez-vous à votre modèle / outil
  • On the loop : améliorez le harnais, pas le code
  • Découpez le travail — petites sessions, un artefact par étape
  • Testez le SDD — même informel, structurer le besoin change tout
