Claude Code : pourquoi c'est différent

Un agent dans le terminal

  • Utilise toutes les CLIs : GitHub CLI, npm, rg, kubectl ...
  • CLAUDE.md : contexte partagé avec les règles
  • Commands : répéter les prompts facilement
  • Édition automatique des fichiers
  • Hooks(juin) : déterministe

Une commande = beaucoup de code produit

"J'ai commencé à pousser toutes les mécaniques : le CLAUDE.md pour le contexte partagé, les commands pour répéter les prompts facilement." "Avant, il fallait écrire un petit moment. Maintenant, une commande pouvait écrire beaucoup de code." Mode YOLO (skip permissions) car tâche de fond sur environnement de dev, pas de risque. "Je lançais toujours en mode skip permissions pour éviter d'être prompté."

Le vrai shift

Prompt Engineering

Context Engineering

Comment structurer le contexte pour que l'IA fasse du bon travail ?

"On n'est pas du tout au prompt engineering. Je pense que le mode est totalement passé. On est directement sur le context engineering, comment améliorer le contexte." "Le prompt doit être le minimum variable possible. En réalité, qu'il y ait très peu de variantes. Quelques milliers de tokens de prompt, c'est pas grave." Le but : mettre un maximum de choses stables dans le contexte pour maximiser le cache.

Les solutions qui marchent

Ce que j'ai mis en place pour résoudre ces problèmes

Découper en sessions

Ne jamais chaîner dans le même prompt

  • Hooks Claude Code : sauvegarde des fichiers, prompts, résumé
  • Nouvelle session = contexte propre + artefacts précédents
  • Le prompt varie peu, le contexte stable est en cache

Cache KV : vos inputs stables sont ~4-5x moins chers

"Les hooks pouvaient être lancés quand la conversation était finie ou quand un tool était fini." "Généralement on les utilisait pour faire des notifications, avoir une alerte quand c'est fini." "On pouvait référencer un document pour éviter de le charger dans le contexte." Il y a un lien vers la personne qui avait mis ça en place de manière encore plus poussée.

Structurer le besoin

! Besoin pas formalisé, pas uniformisé = l'IA a trop de liberté

La solution : des artefacts

Chaque étape produit un artefact qui sert de base à la suivante

"Le but c'est de faire le maximum de requirements. C'est le cœur pour avoir un bon résultat, c'est de limiter les possibilités de l'IA. Et c'est l'avantage du SDD." "Il faut découper le plus petit possible. Ça marche comme le développement. Plus c'est petit, plus c'est facile à développer, tester, déployer. Itérer plus vite sur les erreurs, avoir le feedback utilisateur le plus vite possible." La phase de clarification dans SpecKit : questions posées pour le besoin. L'IA est autonome sur les décisions techniques, l'humain décide sur le fonctionnel/métier.

Pas encore d'outil en prod

"Le SDD ne vient pas du tout du monde de l'IA. Mais là, ça va nous intéresser dans le contexte de l'IA." SpecKit, Kiro (cf. présentation de Mehdi pour ceux qui ont vu, c'est totalement ça). Le niveau 2 (Spec-Anchored) : "C'est le niveau qui m'intéresse, que j'ai essayé de mettre en place." Le niveau 3 (Spec-as-Source) : "Vous modifiez la doc, ça modifie le code. Vous n'écrivez jamais le code." Den Delimarsky, créateur de SpecKit (ex-GitHub), embauché par Anthropic. A travaillé sur la planification et les tâches de Claude Code, maintenant sur MCP. Ref: Birgitta Bockeler (Thoughtworks) — martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html

Le workflow SDD standard

Spec
→
Plan
→
Tasks
→
Implement

Chaque étape = un artefact qui sert de point de départ pour la suivante

Chaque étape dans une session séparée (contexte propre)

C'est le workflow de base du SDD, tel que proposé par SpecKit. "Surtout, ne faites pas l'erreur de lancer à la chaîne dans le même prompt. Ça ne sert à rien. Lancez dans une nouvelle session. Ça repart avec un contexte clair." "Le plan : c'est lui qui doit vraiment avoir toute l'intelligence parce que c'est lui qui analyse le code et qui dit 'Ok, là, tu dois avoir cette construction. Tu dois changer ce fichier.' Si vous avez des limitations de coût, c'est ici que vous devez mettre votre modèle le plus performant." Mon workflow perso ajoute des étapes (simplify, review, doc) — on verra ça en démo devant l'app.

Est-ce que le SDD est indispensable ?

Non.

Tout le monde fait un peu du SDD dès qu'il planifie avant d'implémenter.

La différence : enregistrer les specs comme artefacts persistants.

"Aujourd'hui, Claude Code vous propose automatiquement : il vous fait la planification, il vous dit 'ok, clear le contexte', et on repart du plan. C'est la bonne pratique." "Quand vous utilisez d'autres outils qui ne sont pas aussi développés, une fois que vous faites votre planification, demandez à générer un artefact dans votre commande plan." Quand c'est utile : projet structuré (type entreprise), modèle moins performant (Mistral → "clairement c'est une catastrophe sur la gestion du code"), besoin de traçabilité, agent factory. "Depuis un mois, vous avez 1M de tokens de contexte au même prix que 200K. Ça change beaucoup."

Où se placer dans la boucle ?

Outside
Vibe coding
L'humain décrit, l'agent fait tout. Mais la qualité interne compte toujours.
In the loop
Revue ligne par ligne
L'humain inspecte tout. Mais il devient le goulot d'étranglement.
On the loop
Harness Engineering
Améliorer le harnais (rules, specs, workflow), pas l'artefact.

C'est exactement ce que j'ai fait sur ai-board. Voyons les résultats.

Ref: Kief Morris (Thoughtworks) — "Humans and Agents in Software Engineering Loops" (martinfowler.com) C'est exactement ce qu'on fait : améliorer le CLAUDE.md, la constitution, le workflow. Pas corriger le code individuellement, mais corriger le processus qui produit le code. Quand un résultat ne va pas : on ne corrige pas l'artefact, on modifie le harnais. "Maintenant, voyons ce que ça donne concrètement sur ai-board."

Alors, prêt à arrêter de coder ?

Ma réponse

Non.

Parce que j'aime ça.

Mais : 95% de mon code pourrait être écrit par l'IA.

L'écriture du code n'est plus nécessaire.

"Moi non, parce que j'aime ça, coder. J'aime écrire du code. On peut voir que là, j'ai mon clavier. C'est justement pour saisir. J'aime les vim motion et tout. J'aime taper sur un clavier." "Est-ce que je travaillerais sur des projets rédigés en full IA ? Oui." "Est-ce qu'aujourd'hui sur mon projet actuel je pourrais faire 95% de mon code écrit via l'outil ? Oui. Je n'aurais pas besoin de taper de ligne de code."

L'avertissement

Si vous n'aimez pas relire, vous perdrez le contrôle.

PR acceptées sans relecture = danger

Erreur en prod = votre responsabilité, pas celle de l'IA.

"Si ça ne vous plaît pas, je peux garantir que vous finirez par ne plus relire correctement. Et au bout d'un moment, vous aurez tellement accepté de PR du code sans relecture, que vous ne maîtriserez plus rien." "Et puis s'il y a une erreur, ça sera de votre faute en prod. Je ne pense pas que la responsabilité sera l'IA avant un moment." "Chacun garde à sa porte et fait un peu comme il veut."

Rappel : On the loop

On n'améliore pas le code.
On améliore le harnais qui produit le code.

Rules, specs, workflow, constitution, simplify...

C'est ce qu'on a vu en démo. Et ça se voit dans les résultats.

Callback rapide au concept présenté avant la démo. Ici c'est le moment de faire la synthèse : tout ce qu'on a vu — sessions, rules, SDD, le workflow — c'est du harness engineering. C'est comme ça qu'on reste "on the loop" sans être le goulot d'étranglement.
